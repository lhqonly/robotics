# 电机控制接口抽象设计：先接 CyberGear，后续可换 CubeMars/其他电机

> 状态：草案。
> 日期：2026-07-09。
> 背景：先采购小米 CyberGear 做低成本可行性验证，但工程接口必须支持后续快速切换 CubeMars AK 系列或其他 CAN 力矩电机。

## 1. 设计结论

当前建议：

1. 第一阶段先用 **小米 CyberGear**，原因是便宜、24V、一体驱动、CAN 控制，适合桌面台架快速验证。
2. 代码和 ROS 接口不直接暴露 CyberGear 协议，而是定义一套 **厂商无关的 Joint/Motor 抽象接口**。
3. CyberGear、CubeMars、未来其他电机都作为 `motor_backend` adapter 接入。
4. 上层控制永远只看“关节目标”和“关节状态”，不关心具体电机的 CAN ID 编码、单位换算、模式切换细节。
5. 调试接口必须保留 raw CAN / 厂商参数透传能力，但默认控制链路不能依赖 raw vendor command。
6. `motor control` 与现有 ROS `/com/` 通信节点**并列设计**，不要包含进 `com node`。`/com/` 负责链路健康，`/motor/` 负责电机/关节控制语义。

目标结构：

```text
SoC / PC ROS2
  |
  |  /motor/tp_joint_target    目标助力/阻抗/轨迹片段
  v
MCU joint controller
  |
  |  motor_hal_send_target()
  v
Motor HAL, vendor-neutral
  |
  +-- cybergear_backend.c      小米 CyberGear CAN 适配
  +-- cubemars_ak_backend.c    CubeMars AK CAN 适配
  +-- mock_motor_backend.c     无硬件仿真/测试
```

## 2. 已知电机事实

### 2.1 小米 CyberGear

用于第一阶段低成本验证。

已知事实：

- 小米官方商城页面价格为 `499 元`，但可能存在地区缺货。
- 电机通信为 CAN 2.0，波特率 `1Mbps`，扩展帧格式。
- 额定工作电压 `24VDC`，允许最大电压 `28VDC`。
- 额定工作电流约 `6.5A`，峰值/最大允许电流资料中标到 `23A`。
- 减速比 `7.75:1`，单圈绝对编码器 `14bit`。
- 支持运控模式、电流模式、速度模式、位置模式等。
- 资料/社区生态足够做验证，但官方调试器链路更偏特定 USB-CAN/AT 协议，Linux SocketCAN 方向需要我们自己整理驱动。

采购时建议一起买：

- CyberGear 电机 x1
- 24V 电源，建议台架验证先选 `24V / >=10A`
- USB-CAN，优先选 Linux SocketCAN 兼容型号；如果只能买到 YourCee/CH340 类串口 USB-CAN，也要单独封装 transport
- XT30(2+2) 线材或转接板
- CAN 终端电阻 `120Ω`
- 急停、保险、限流、机械固定夹具

### 2.2 CubeMars AK 系列

用于后续更接近外骨骼关节的验证。

已知事实：

- AK 系列是电机、减速器、驱动一体化 actuator。
- 官方文档明确 CAN 扩展帧协议，servo mode 支持 duty/current/velocity/position/position-velocity 等模式。
- current loop 中 `torque = Iq * KT`，可以作为力矩环接口使用。
- CubeMars AK 有现成 Python API `TMotorCANControl`，适合 PC/ROS 快速打样。
- 价格明显高于 CyberGear：AK40/AK45 最便宜，AK60/AK70/AK80 更接近外骨骼关节，但成本更高。

建议后续候选：

| 阶段 | 型号 | 目的 |
|---|---|---|
| 低成本接口验证 | AK40-10 / AK45-10 | 验证 CubeMars adapter，不追求真实负载 |
| 第一块工程验证 | AK60-6 V3.0 | 价格和能力折中 |
| 更接近关节验证 | AK70-9 / AK70-10 | 更像膝/髋这类外骨骼关节 |
| 高扭矩验证 | AK80-9 或更大 | 后续真实负载阶段 |

### 2.3 Tony607/Cybergear 参考工程评估

用户补充的 `Tony607/Cybergear` 是一个现成的小米微电机上手工程，适合作为 CyberGear 第一阶段 bring-up 参考，而不是直接作为长期架构边界。

该仓库包含：

- `cybergear/pcan_cybergear.py`：基于 `python-can` + PCAN 的 CyberGear 控制封装。
- `notebooks/pcan*.ipynb`：单轴/多轴 PCAN 调试和示教 notebook。
- `01_web_simple_control`：Flask + WebSocket + 串口 AT 帧的简单 Web 控制。
- `02_esp32_micropython`：ESP32 MicroPython CAN 玩法。
- `03_whistle_control`：口哨频率映射到电机速度，README 标明 USB-CAN 适配器为 PCAN。
- `04_gpt_action_control`：HTTP/WebSocket 转发到本地机械臂上位机，并播放 CSV 示教轨迹。
- `torque_sensor_osc` 子模块：外置扭矩传感器方向，适合后续台架闭环测力参考。
- `stepper_gripper` 子模块：与小米电机共享 CAN 总线和电源的闭环机械爪参考。

对我们设计的启发：

1. **Phase M0 可直接借鉴 PCAN + python-can 路线**：它已经验证了 `can.interface.Bus(interface="pcan", channel="PCAN_USBBUS1", bitrate=1000000)` 这类 PC 直连控制方式。我们应把 PC 直连 CyberGear 的第一版工具做成 `python-can` backend，优先兼容 PCAN，同时预留 SocketCAN。
2. **CyberGear adapter 的协议元素可以先从该仓库抽取 contract**：命令类型覆盖 `GET_DEVICE_ID`、`MOTOR_CONTROL`、`MOTOR_ENABLE`、`MOTOR_STOP`、`SET_MECHANICAL_ZERO`、`SET_MOTOR_CAN_ID`、`PARAM_TABLE_WRITE`、`SINGLE_PARAM_READ/WRITE`、`FAULT_FEEDBACK`；运行模式覆盖运控、位置、速度、电流。
3. **单位映射要进入 adapter，不进入上层接口**：该仓库里把位置、速度、力矩、Kp、Kd 映射到 16bit 区间，并解析反馈中的 position/velocity/torque/temperature。我们要把这些映射固化为 `cybergear_frame_codec` 单测，不能让 ROS topic 或 joint controller 知道这些厂商范围。
4. **串口 AT 帧 demo 只能做低门槛调试参考**：`01_web_simple_control` 直接发送十六进制 AT 帧到 `COM3@921600`，对快速确认电机动作有帮助，但不适合作为正式控制链路。正式链路应优先走 `python-can`/SocketCAN/PCAN 这类标准 CAN API。
5. **多轴示教和 CSV 回放对外骨骼台架有参考价值**：但它属于动作/轨迹层，应该映射到 `/motor/act_run_joint_trajectory` 或调试工具，不应该绕过 `JointTarget` 和 safety state machine。
6. **外置扭矩传感器值得单独建 sensor 抽象**：不要把外置扭矩传感器绑进 CyberGear adapter。它应作为 `/sensor/` 或 `/motor/tp_joint_external_wrench` 一类独立输入，未来可用于校准电机估算力矩。

因此本设计保持不变：Tony607 工程用于 **bring-up 参考和协议 contract 样本**；我们自己的长期接口仍以 `exo_motor_msgs + motor_backend adapter` 为边界。

## 3. 分层边界

### 3.1 ROS/SoC 层：表达“人体/控制目标”

ROS 层不应该发布“CyberGear 通信类型 18”或“CubeMars extended ID”这类厂商命令。

ROS 层应该发布：

- 哪个关节
- 控制模式
- 目标位置/速度/力矩
- 阻抗参数
- 限幅
- 命令时效
- 安全策略

建议 namespace：

```text
/ctrl/   控制算法、人体意图、助力策略
/motor/  电机/关节执行与状态
/com/    现有 ROS2 <-> micro-ROS 通信链路
```

### 3.1.1 `/com/` 与 `/motor/` 的节点边界

Elon 评审意见：`motor control` 不应该包含在 `com node` 中，而应该与 `/com/` 并列。原因是这两个模块的职责、故障模型和后续演进方向都不同。

`/com/` 负责“路通不通、稳不稳、延迟多少”：

- PC 与 STM32/micro-ROS 是否连上。
- 串口、micro_ros_bridge、topic match 是否正常。
- RTT、丢包、重复包、stale target、链路健康。
- MCU 基础状态上报。
- 通信压测和回归验证。

`/motor/` 负责“电机/关节应该怎么动、动得是否安全”：

- 使能/失能电机。
- 设置力矩、速度、位置、阻抗、轨迹目标。
- 读取关节状态、电机估算力矩、电流、电压、温度。
- 清故障、设零点、限幅、预检。
- 抽象 CyberGear、CubeMars 和其他厂商电机差异。

推荐 ROS 节点与 topic 关系：

```text
/com/
  node_com_cmd
  node_com_mcu
  tp_link_health
  tp_mcu_status

/motor/
  node_motor_ctrl
  tp_joint_target
  tp_joint_state
  tp_motor_health
  srv_enable_joint
  srv_set_zero
  srv_clear_fault

/ctrl/
  node_assist_ctrl
  node_gait_ctrl
```

典型控制流：

```text
SoC/PC 上层控制算法
        |
        v
/ctrl/node_assist_ctrl
        |
        v
/motor/tp_joint_target
        |
        v
/motor/node_motor_ctrl
        |
        v
STM32 本地 10kHz 控制环 + CAN 电机驱动
        |
        v
CyberGear / CubeMars / 其他电机
```

关键约束：

1. `com node` 不理解电机命令含义，只提供通信承载和链路诊断。
2. `motor node` 不直接管理 micro_ros_bridge 或串口桥，只消费/发布 `/motor/` 语义接口。
3. 固件物理实现可以是同一个 MCU binary，但代码结构必须分成 `com`、`motor`、`control_loop`、`vendor_driver` 四类模块。
4. STM32 资源紧张时，可以只有一个 micro-ROS executor 或一个固件主循环，但 ROS topic/service 语义仍然按 `/com/` 与 `/motor/` 分开。
5. 更换电机厂商时，只替换 `motor_backend` 和配置，不改 `/com/` 链路验证接口，也不改 `/motor/` 上层控制契约。

### 3.2 MCU Joint Controller 层：表达“关节控制”

MCU 侧负责：

- 接收最新目标
- 做本地插值/限幅/安全保护
- 10kHz 本地控制 tick
- 将关节目标转换为 motor HAL 命令
- 监控电机状态和故障

MCU 侧不应该让上位机直接以 200Hz 控原始电流环。上位机下发的是目标和参数，MCU 本地闭环决定每个 tick 如何执行。

### 3.3 Motor HAL 层：厂商无关能力接口

Motor HAL 是切换厂商的关键边界。

建议最小 C 接口：

```c
typedef enum {
  MOTOR_MODE_DISABLED = 0,
  MOTOR_MODE_ZERO_TORQUE,
  MOTOR_MODE_TORQUE,
  MOTOR_MODE_VELOCITY,
  MOTOR_MODE_POSITION,
  MOTOR_MODE_IMPEDANCE,
  MOTOR_MODE_TRAJECTORY,
  MOTOR_MODE_CALIBRATION,
} motor_mode_t;

typedef struct {
  uint8_t joint_id;
  motor_mode_t mode;
  float position_rad;
  float velocity_rad_s;
  float torque_nm;
  float kp_nm_per_rad;
  float kd_nm_s_per_rad;
  float max_torque_nm;
  float max_velocity_rad_s;
  uint32_t command_seq;
  uint32_t ttl_us;
  uint32_t flags;
} motor_target_t;

typedef struct {
  uint8_t joint_id;
  float position_rad;
  float velocity_rad_s;
  float torque_est_nm;
  float current_a;
  float bus_voltage_v;
  float temperature_c;
  motor_mode_t mode;
  uint32_t fault_bits;
  uint32_t last_command_seq;
  uint32_t sample_age_us;
} motor_state_t;

typedef struct {
  bool supports_torque;
  bool supports_velocity;
  bool supports_position;
  bool supports_impedance;
  bool supports_trajectory;
  bool has_output_encoder;
  float torque_resolution_nm;
  float position_resolution_rad;
  uint32_t max_command_hz;
} motor_capability_t;
```

建议 adapter 函数：

```c
bool motor_backend_probe(uint8_t bus_id, uint8_t motor_id);
bool motor_backend_enable(uint8_t motor_id);
bool motor_backend_disable(uint8_t motor_id);
bool motor_backend_clear_fault(uint8_t motor_id);
bool motor_backend_set_zero(uint8_t motor_id);
bool motor_backend_send_target(const motor_target_t *target);
bool motor_backend_read_state(uint8_t motor_id, motor_state_t *state);
bool motor_backend_get_capability(uint8_t motor_id, motor_capability_t *cap);
bool motor_backend_get_param(uint8_t motor_id, uint16_t param_id, float *value);
bool motor_backend_set_param(uint8_t motor_id, uint16_t param_id, float value);
```

厂商差异只允许出现在：

- `cybergear_backend.*`
- `cubemars_ak_backend.*`
- `motor_model_config.yaml/json/c`
- 单位换算表
- fault bits 映射表

不允许出现在：

- 上层 ROS topic
- 关节控制算法
- 安全状态机
- 轨迹/助力策略

## 4. 统一 ROS 接口草案

后续建议新增独立消息包：

```text
exo_motor_msgs
```

不要把所有 motor 消息继续塞进当前最小通信验证用的 `exo_msgs`。当前 `exo_msgs` 主要服务 `/com/` 链路验证；电机控制进入新模块后，应单独成包，避免语义混杂。

### 4.1 Command Topic

```text
/motor/tp_joint_target
```

方向：

```text
SoC/PC ROS2 -> MCU
```

语义：

```text
Header header
uint32 seq
uint8 joint_id
uint8 control_mode

float64 position_rad
float64 velocity_rad_s
float64 torque_nm
float64 kp_nm_per_rad
float64 kd_nm_s_per_rad

float64 max_torque_nm
float64 max_velocity_rad_s
float64 max_position_rad
float64 min_position_rad

uint32 ttl_us
uint32 flags
```

关键点：

- `control_mode` 是统一枚举，不是厂商 mode ID。
- `ttl_us` 必须有。过期目标不能继续执行。
- `max_*` 是每条命令携带的最后防线，MCU 还要叠加本地全局限幅。
- `flags` 可用于 `relative_position`、`hold_if_expired`、`require_fresh_state` 等策略。

### 4.2 State Topic

```text
/motor/tp_joint_state
```

方向：

```text
MCU -> SoC/PC ROS2
```

语义：

```text
Header header
uint32 seq
uint8 joint_id
uint8 control_mode

float64 position_rad
float64 velocity_rad_s
float64 torque_est_nm
float64 current_a
float64 bus_voltage_v
float64 temperature_c

uint32 fault_bits
uint32 vendor_fault_bits
uint32 last_target_seq
uint32 sample_age_us
bool target_fresh
bool enabled
```

关键点：

- `fault_bits` 是统一故障位。
- `vendor_fault_bits` 保留原始厂商故障，便于定位。
- `last_target_seq` 用于闭环确认 MCU 执行到了哪条目标。
- `sample_age_us` 用于判断状态新鲜度。

### 4.3 Health Topic

```text
/motor/tp_motor_health
```

语义：

```text
Header header
uint8 bus_id
uint8 joint_count
uint64 targets_received
uint64 targets_applied
uint64 stale_targets
uint64 motor_tx
uint64 motor_rx
uint64 motor_timeout
uint64 motor_fault
float64 target_apply_latency_p99_ms
float64 can_gap_p99_ms
bool reconciles
```

这相当于 `/com/tp_link_health` 的 motor 版，但关注的是“目标是否被执行、电机是否响应、CAN 是否健康”。

## 5. 服务/动作接口草案

### 5.1 安全和生命周期服务

```text
/motor/srv_enable_joint
/motor/srv_disable_joint
/motor/srv_clear_fault
/motor/srv_set_zero
/motor/srv_set_control_mode
/motor/srv_set_joint_limits
```

语义要求：

- `enable` 前必须通过 preflight：CAN 在线、电压正常、温度正常、位置在限位内、急停未触发。
- `disable` 默认进入安全零力矩或厂商 stop，不允许继续保持旧目标。
- `set_zero` 必须只允许在 calibration mode 下执行。

### 5.2 调试/诊断服务

```text
/motor/srv_scan_bus
/motor/srv_get_vendor_info
/motor/srv_get_param
/motor/srv_set_param
/motor/srv_dump_config
/motor/srv_inject_test_target
```

注意：

- `set_param` 是危险接口，默认只允许台架/调试模式。
- 所有参数修改必须记录日志，包含旧值、新值、操作者、时间。
- 调试接口不参与实时控制链路，不允许在控制热路径里阻塞。

### 5.3 动作接口

```text
/motor/act_calibrate_joint
/motor/act_home_joint
/motor/act_run_joint_trajectory
/motor/act_sine_sweep
```

动作接口用于低频、可中断、有进度反馈的过程，不用于 200Hz 实时目标流。

## 6. 控制模式脑暴

外骨骼里不同关节会需要不同模式，建议统一抽象如下：

| 模式 | 用途 | 典型关节/场景 | 风险 |
|---|---|---|---|
| `DISABLED` | 断使能/不可执行 | 上电默认、故障 | 不能误保持力矩 |
| `ZERO_TORQUE` | 零力矩透明跟随 | 穿戴、标定、手动拖动 | 实际是否真零取决于厂商控制 |
| `TORQUE` | 直接力矩/电流助力 | 助力验证、力控策略 | 最危险，必须限幅/限斜率 |
| `VELOCITY` | 速度控制 | 台架验证、关节释放测试 | 易超限，必须位置保护 |
| `POSITION` | 位置保持/点到点 | 标定、低速机械验证 | 人体交互时可能僵硬 |
| `IMPEDANCE` | `tau = kp*(q_ref-q)+kd*(dq_ref-dq)+ff` | 外骨骼主模式候选 | 参数不当会振荡 |
| `TRAJECTORY` | 轨迹片段、本地插值 | 步态片段、重复动作 | 必须可急停 |
| `CALIBRATION` | 零位、方向、比例标定 | 上电/维护 | 只能台架执行 |
| `RAW_VENDOR` | 厂商透传 | bring-up 和抓问题 | 只能调试，不进入正式控制 |

第一阶段建议只实现：

1. `DISABLED`
2. `ZERO_TORQUE`
3. `POSITION`
4. `VELOCITY`
5. `TORQUE`

第二阶段再上：

1. `IMPEDANCE`
2. `TRAJECTORY`
3. `CALIBRATION` 完整流程

## 8. 安全状态机

建议所有关节共享统一状态机：

```text
BOOT
  -> BUS_READY
  -> MOTOR_DISCOVERED
  -> CALIBRATED
  -> ENABLED_ZERO_TORQUE
  -> ACTIVE_CONTROL
  -> FAULT
  -> E_STOP
```

关键规则：

- 上电默认 `DISABLED` 或 `ZERO_TORQUE`，不能默认进入助力。
- 目标命令超时，必须从 `ACTIVE_CONTROL` 降级到 `ZERO_TORQUE` 或安全保持。
- 电机状态超时，必须退出 `ACTIVE_CONTROL`。
- 位置越界、速度越界、温度越界、电压异常、CAN timeout 都进入 `FAULT`。
- `E_STOP` 只能人工复位。

## 9. 调试接口必须支持的观察量

为了后续排查“跟不跟脚”和“电机有没有按目标执行”，必须能看这些：

### 9.1 实时链路

- PC/ROS 目标发布时间
- MCU 收到目标时间
- MCU 应用目标到控制 tick 的时间
- CAN 发出 motor command 时间
- motor state 回来的时间
- target seq 到 motor state 的闭环确认

### 9.2 电机本体

- position
- velocity
- torque estimate / current
- temperature
- bus voltage
- fault code
- enabled / mode
- last command age

### 9.3 CAN 总线

- TX/RX 帧计数
- timeout 计数
- bus-off / error-passive / error-warning
- raw frame trace，可限频发布
- p95/p99 command gap

### 9.4 控制质量

- target age
- tracking error
- torque saturation count
- position limit clamp count
- velocity limit clamp count
- stale target count
- mode transition count

## 10. 阶段化落地路线

Elon 评审后的阶段划分如下。核心原则是：**先把厂商无关接口固定住，再让 CyberGear 成为第一个 adapter；CubeMars 作为后续分支复用同一契约**。

### Phase M0：PC 直连 CyberGear / mock

目标：最快确认两件事：

1. 没有真实电机时，mock backend 能完整跑通 `/motor/` 统一接口。
2. CyberGear 到货后，PC 可以通过 USB-CAN 直接验证电机能转、模式能切、状态能读。

架构：

```text
ROS2 node_motor_pc
  -> python-can / PCAN or SocketCAN / USB-CAN
  -> CyberGear
```

推荐先做两个互相隔离的小工具：

```text
motor_cybergear_probe.py       只做扫描、enable/disable、读状态
motor_cybergear_benchtop.py    通过统一 ROS topic/service 做低速 position/velocity/torque 验证
mock_motor_backend.py          无硬件时模拟 JointTarget -> JointState
```

第一版可以参考 Tony607/Cybergear 的 `CANMotorController`，但要做三件事：

1. 把 PCAN 固定参数抽成配置，接口形如 `--interface pcan --channel PCAN_USBBUS1 --bitrate 1000000`，后续可换成 `--interface socketcan --channel can0`。
2. 把 CyberGear 帧编解码拆成纯函数，做离线单测，不依赖真实电机。
3. 把 demo 里的 enable/disable/position/speed/current/control mode 映射到统一 `JointTarget` / `JointState`，而不是把 CyberGear 原始命令暴露给上层。

M0 验收：

- mock 模式下能用统一 `/motor/tp_joint_target` 生成 `/motor/tp_joint_state`。
- PC 直连 CyberGear 时能扫描到电机。
- 能 enable/disable。
- 能 clear fault。
- 能 set zero。
- 能低速 position 正反转。
- 能 velocity 小速度运行。
- 能 current/torque 小力矩输出。
- 能读取 position/velocity/current/temperature/fault。

这阶段允许 PC 直接控电机，但 ROS topic/service 必须使用统一接口，不直接暴露 CyberGear。

### Phase M1：ROS 接口和消息包

目标：建立厂商无关的 ROS 契约，为 M0/M2/M3 共用。

建议新增：

```text
ros2_ws/src/exo_motor_msgs/
  msg/JointTarget.msg
  msg/JointState.msg
  msg/MotorHealth.msg
  srv/EnableJoint.srv
  srv/DisableJoint.srv
  srv/ClearMotorFault.srv
  srv/SetJointZero.srv
  srv/SetJointMode.srv
  srv/GetMotorParam.srv
  srv/SetMotorParam.srv
```

M1 验收：

- `colcon build` 和 `colcon test` 通过。
- `/motor/tp_joint_target`、`/motor/tp_joint_state`、`/motor/tp_motor_health` 可被 `ros2 interface show` 和测试节点使用。
- 消息字段覆盖 joint id、mode、位置、速度、力矩、阻抗参数、限幅、ttl、seq、fault。
- 不出现 CyberGear/CubeMars 厂商字段。
- mock 节点证明 seq、ttl、限幅字段能被消费。

### Phase M2：MCU 订阅 `/motor/tp_joint_target` 并本地控制

目标：把真实链路变成：

```text
PC/ROS 200Hz target -> STM32 micro-ROS -> STM32 CAN -> CyberGear
```

注意：M2 的重点不是 CyberGear 协议细节，而是 MCU 侧统一 joint controller。

M2 验收：

- 10kHz 控制 tick 中消费 latest target
- `target_seq -> applied_seq -> motor_state` 可追踪
- 超时后安全降级
- 单电机台架 p99 目标应用延迟可测
- 没有电机时可用 mock backend 或空 backend 验证控制环和安全状态机
- MCU 端仍可以只有一个 `/node_mcu`，但内部代码拆成 `com`、`motor`、`control_loop`、`vendor_driver`

### Phase M3：CyberGear CAN backend

目标：在 M2 的 Motor HAL 下实现第一个真实厂商 backend：

```text
motor_backend = cybergear
```

M3 验收：

- STM32 通过 CAN 控 CyberGear。
- CyberGear 帧编解码有离线单测。
- enable/disable/clear fault/set zero/position/velocity/torque 小范围动作可用。
- CyberGear position/velocity/current/temperature/fault 映射到统一 `JointState` / `MotorHealth`。
- 厂商故障码进入 `vendor_fault_bits`，统一故障进入 `fault_bits`。
- 厂商单位换算只存在于 CyberGear adapter/codec，不泄露到 `/motor/` ROS 接口。

### Phase M4：验证、安全与台架验收

目标：把“能动”升级为“可重复、安全、可观测”。

M4 验收：

- 上电默认 `DISABLED` 或 `ZERO_TORQUE`。
- ttl 过期、电机状态超时、位置/速度/温度/电压异常都能进入安全降级或 `FAULT`。
- 急停路径可验证。
- 200Hz SoC target + 10kHz MCU control tick + 1Mbps CAN 在单电机台架下能稳定压测。
- Gill 有一套可重复执行的 smoke/soak/safety 验收脚本。
- 验收报告能回答：p99 目标应用延迟、worst case、丢包/超时计数、stale target 计数、故障恢复路径。

### 后续分支：CubeMars adapter

目标：不改 ROS topic、不改关节控制器，只替换：

```text
motor_backend = cybergear -> cubemars_ak
```

CubeMars 分支验收：

- 同一套 `JointTarget` 可以驱动 CubeMars
- 同一套 `JointState` 可以读回 CubeMars
- 厂商 fault 能映射到统一 fault_bits
- 单测证明 CyberGear/CubeMars adapter 均满足 Motor HAL contract

对应任务卡入口：

```text

docs/plan/002-M1-exo_motor_msgs与ROS接口.md
```

## 12. 关键设计取舍

### 12.1 为什么不直接把 CyberGear 协议当 ROS 接口？

因为这样后面换 CubeMars 时，上层控制、调试工具、bag 数据、测试脚本都会一起变。统一接口的价值是让厂商协议变成 adapter 细节。

### 12.2 为什么 ROS topic 用 joint 而不是 motor？

外骨骼控制关心的是“膝关节/髋关节/踝关节”的目标，不是“CAN ID 127 的电机”。一个关节未来可能不是一个电机，可能有传感器、减速器、弹性元件、双电机。所以上层用 joint 语义，底层 adapter 才用 motor 语义。

### 12.3 为什么还保留 raw vendor 调试？

bring-up 阶段一定会遇到厂商文档不清、单位不一致、故障码不明的问题。没有 raw frame/param 入口，排障会很痛苦。但 raw vendor 只能在调试权限下使用，不能成为正式控制路径。

### 12.4 为什么先 PC 直连，再 MCU 接入？

PC 直连可以把问题拆开：

- 电机/供电/CAN/协议是否正常
- ROS 统一接口是否好用
- 再验证 STM32 CAN 和实时控制

这样不会一上来把 micro-ROS、STM32 CAN、电机协议、供电、机械风险全部搅在一起。

### 12.5 分支策略：先 CyberGear 分支，再沉淀共同接口

当前这份设计文档和后续 CyberGear bring-up 代码，适合从 `main` 切出独立分支，例如：

```text
feature/cybergear-motor-control
```

后续 CubeMars 接入再建独立分支，例如：

```text
feature/cubemars-motor-control
```

Elon 推荐的合并节奏：

1. **共同契约先合 main**：`exo_motor_msgs`、`/motor/` topic/service/action 命名、Motor HAL C 接口、mock backend、接口 contract test 这些是跨厂商共同资产，应尽早评审后合入 `main`。
2. **CyberGear 分支只放厂商实现和台架脚本**：`cybergear_backend.*`、`cybergear_frame_codec.py`、PCAN/SocketCAN bring-up 工具、CyberGear 参数表和安全限幅配置留在 CyberGear 分支开发。
3. **CubeMars 分支复用同一契约**：CubeMars 分支只新增 `cubemars_ak_backend.*`、CubeMars codec/test、型号参数配置，不复制或改名 `/motor/` 上层接口。
4. **分支之间不互相依赖**：CubeMars 分支不要从 CyberGear 分支继续开，应该从包含共同契约的 `main` 开，避免把 CyberGear 厂商细节带进 CubeMars。
5. **硬件验证结果再回灌 main**：台架验证中证明通用有效的限幅、状态机、测试工具、文档结论，可以从厂商分支挑出来单独合回 `main`。

推荐提交粒度：

```text
main
  └─ common motor contract
       ├─ feature/cybergear-motor-control
       └─ feature/cubemars-motor-control
```

对应原则：

- `main` 保存“厂商无关接口”和已验证的稳定工具。
- `feature/cybergear-motor-control` 保存小米 bring-up 试错、PCAN/SocketCAN 验证和 CyberGear adapter。
- `feature/cubemars-motor-control` 保存 CubeMars adapter 和型号差异验证。
- 厂商分支里的实验性 commit 可以本地密集一点，但远端 push 前做 squash/整理，避免远端历史过密。
