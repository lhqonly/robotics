# 性能验证记录（2026-07-08）

目标：验证“MCU 本地 1kHz 起步、阶梯到 10kHz 控制基线 + PC/ROS 高频下发 + ROS 状态/链路健康回传”的第一阶段可行性。

## 环境

- 板子：STM32F103RB，USART1 `/dev/ttyUSB0`，921600 8N1，DMA。
- Agent：`tools/run-bridge.sh /dev/ttyUSB0 921600`，默认 `MICROROS_AGENT_VERBOSITY=1`。
- 固件：新增 `com_control_task` 1kHz 本地控制骨架；2/5/10kHz 档切换到 TIM2 ISR；micro-ROS spin/read 等待收紧到 1ms 量级。
- PC 节点：`pc_cmd.launch.py`，QoS `RELIABLE / KEEP_LAST / depth=2`，早期压测使用 `rtt_warn_ms=10`，`rtt_deadline_ms=50`；当前默认诊断 hard deadline 为 `120ms`，并启用 `startup_grace_s=3.0` 排除 PC 节点刚启动时的发现/握手瞬态。高频 latest-target profile 仍显式使用 `best_effort / depth=1`。

### Latest-target status decimation

新增固件编译项 `EXO_STATUS_EVERY_N`：MCU 每条 PC 命令都更新本地 latest target，
但只按比例发布 `/com/tp_mcu_status`。这更贴近“PC 200Hz 下发目标，MCU 本地闭环消费最新目标，状态/链路健康另行回传”的控制分层。

| reliable，`EXO_STATUS_EVERY_N=5` | 200 Hz | 约 14.4 Hz | 约 72 Hz | 比 full echo 约 40Hz 有改善，但仍远低于 200Hz |

## 结论

- 当前 `RELIABLE + micro-ROS serial + 921600 + F103` 往返闭环稳定点约为 20 Hz。
- 200 Hz 目标未达成；瓶颈不是单一 PC timer 或 agent 日志，固件已收紧到 1ms 后仍卡在约 40 Hz 状态回传。
- best-effort 能提高裸 topic 吞吐到约 80 Hz，但不能直接满足“每条控制命令可配对确认”的安全闭环要求。
- 2Mbps 能建链，说明物理层可跑更高波特率；但 reliable 闭环只从约 42Hz 提到约 46Hz，收益不足以支撑 200Hz。
- `EXO_CONTROL_LOOP_HZ=1000/2000/5000/10000` 四档已通过编译验证；2/5/10kHz 使用 TIM2 ISR，不占 control task 栈，RAM 从 15.6KB 降到约 15.0KB。
- 2/5/10kHz 真机运行期烟测均能保持 20Hz PC 命令无 lost；RTT 仍主要落在 20-30ms 区间，说明“MCU 本地闭环提频”和“PC/ROS 往返通信延迟”需要分开优化。
- latest-target 方向有实质收益：`best_effort + status_every_40 + sampled monitor` 反推 MCU 可接收约 190Hz PC 目标；叠加 2kHz/10kHz 本地闭环后仍可保持约 193Hz 等效目标接收。进一步开启 PC 侧 `cmd_catchup_max=1` 后，10kHz/200Hz/status_every_40 60s soak 达到 sampler 等效 `199.20Hz`、PC 累计 `199.243Hz`、`lost=0 duplicate=0`，已经基本达到“PC/ROS 200Hz 下发目标，MCU 本地闭环消费 latest target”的目标形态。继续降到 `status_every_50` 没有收益，当前推荐维持 `status_every_40`。
- 新增 `tools/measure-stack-hwm.sh` 后读到默认 1024-word micro-ROS 栈实际 used≈484/free≈540 words；据此把 `MICROROS_TASK_STACK_WORDS` 从 1024 降到 768，RAM 从 15616B 降到 14592B，仍有 free≈284 words。注意该脚本会通过 GDB 短暂停核，不应和实时 hz 测量同时使用。
- 新增 `tools/run-com-perf.sh` 后，真机 profile 可一键复现：脚本会构建/烧录、启动 bridge、启动 PC node、采样 `/com/tp_mcu_status` 并输出 LinkHealth summary。
- 恢复默认固件后，20Hz smoke 可建图并正常收发；连续短测出现过单次 `lost=1 duplicate=1`，RTT 约 55ms，需继续观察是否为 reset 后瞬态或链路抖动。后续单独复测 20Hz 为 `sent=140 matched=139 lost=0 duplicate=0 inflight=1`。脚本化默认回归状态频率仍为 19.986Hz，但出现 `sent=240 matched=233 lost=6 duplicate=5 inflight=1`，说明 reliable/full-echo 模式的重传/超时抖动仍需继续定位；不影响 latest-target/best-effort 分层方向的结论。
- 上述 default reliable 的 `lost/duplicate` 中，日志显示典型 late echo 在 50-85ms 区间，50ms deadline 太贴近 20Hz 周期与 RTT 尾部；因此后续默认监控先改为 `rtt_warn_ms=10`、`rtt_deadline_ms=100`：10ms 仍作为滞后风险预警，100ms 才判 LOST。改为 100ms 后脚本回归状态频率 20.010Hz，末尾 `sent=248 matched=246 lost=1 duplicate=0 inflight=1`；剩余 1 次为 `seq=33 waited_ms=103.945`，属于真实长尾超时，后续仍需继续定位 full-echo reliable 的偶发 >100ms 抖动。
- PC 节点新增 `wire_sent/wire_rate_hz/wire_window_hz` 日志后确认：200Hz 目标下，rclpy 实际 wire 发送约 191-194Hz；把 deadline sweep 从 5ms 放宽到 20ms 后，状态间隔更稳定（本轮 max 0.233s），因此 `pc_cmd.launch.py` 与 `tools/run-com-perf.sh` 默认 `sweep_period_s=0.02`。
- PC 节点默认关闭逐条 matched INFO 日志，并把 soft RTT WARN 日志按 1s 节流后，default reliable smoke 改善为 `status_hz=19.897`、`max_gap_s=0.076`、`wire_window_hz=20.000`、`sent=243 matched=242 lost=0 duplicate=0 inflight=1`。后续恢复默认固件后一轮短测出现过 `max_gap_s=1.197/lost=1`，立即不烧录复测恢复到 `status_hz=20.004`、`max_gap_s=0.062`、`lost=0 duplicate=0 inflight=1`；说明偶发长尾仍存在，但热路径日志降噪有实际收益，后续高频 profile 默认保持降噪。
- 为避免 `ros2 topic hz` 单一 CLI 视角误判，PC summary 新增 `sent_window_hz/matched_window_hz/target_window_hz`，`tools/run-com-perf.sh` 会解析最后一个 summary 窗口。默认 reliable 复测得到 `status_hz=19.997`、`pc_matched_window_hz=19.999`、`pc_target_window_hz=19.999`、`max_gap_s=0.073`、`lost=0 duplicate=0 inflight=1`，两种观测口径一致。
- 用窗口指标复测高频推荐 profile（10kHz 本地闭环、200Hz PC、best-effort、`status_every_40`）：`status_hz=4.841`、`pc_matched_window_hz=4.999`、`pc_target_window_hz=199.972`、`max_gap_s=0.248`、`lost=0 duplicate=0 inflight=0`。这说明稳态窗口已达到“PC/ROS 200Hz 下发目标，MCU 本地闭环消费 latest target”的目标形态。
- 恢复默认 reliable 后连续两轮短测仍可复现 `ros2 topic hz` 约 1.15s 长间隔与累计 `lost=1`，但最后一个 PC summary 窗口保持 `pc_target_window_hz≈20`；这类偶发长尾/CLI 观测差异仍列为未解决项，需要更长 soak 或非 CLI 采样器确认根因。
- 新增 `ros2 run exo_cmd status_sampler` 作为非 CLI 采样器，并接入 `tools/run-com-perf.sh`。默认 reliable smoke 中 sampler 与 `ros2 topic hz` 一致：`sampler_hz=19.997`、`sampler_max_gap_s=0.063`、`status_hz=19.995`、`lost=0 duplicate=0 inflight=1`。后续判断长尾时以 sampler + PC summary + CLI 三个视角交叉验证。
- 用 sampler 复测高频推荐 profile 时，CLI 再次出现 `max_gap_s=1.268` 并把等效目标接收拉低到 `183.12Hz`，但 sampler 记录 `sampler_hz=4.845`、`sampler_max_gap_s=0.232`、等效 `sampler_target_rx_hz=193.80`，PC summary 末窗口 `pc_target_window_hz=199.972`、`lost=0 duplicate=0 inflight=0`。因此当前判断：CLI 长间隔主要是观测工具抖动；高频链路稳态窗口仍接近 200Hz。
- `tools/run-com-perf.sh` 现在解析 PC summary 的累计 `target_rate_hz`，避免 `status_every_40` 在 1s summary 窗口里因 4/5 个样本边界抖动而误读成 160/200Hz 跳变。复测 10kHz/200Hz/best-effort/status_every_40，60s sampler 为 `4.827Hz`（等效 `193.08Hz`），PC 累计 `pc_target_rate_hz=193.382`，LinkHealth `sent=349 matched=349 lost=0 duplicate=0 inflight=0`；CLI 仍显示 `max_gap_s=1.362`，因此高频推荐 profile 的判据以后以 sampler + PC 累计 rate 为主。
- PC 节点新增 `cmd_catchup_max`，默认 0；高频 latest-target profile 显式使用 `cmd_catchup_max=1`，在 rclpy timer 晚到时最多补发 1 条命令，避免长期 wire rate 停在约 194Hz。复测结果：`pc_wire_rate_hz=200.003`、`pc_target_rate_hz=199.243`、`sampler_target_rx_hz=199.20`、`lost=0 duplicate=0 inflight=0`。该补偿不作为 reliable/full-echo 默认值，避免用突发掩盖诊断链路调度问题。
