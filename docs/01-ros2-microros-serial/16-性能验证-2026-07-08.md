# 性能验证记录（2026-07-08）

目标：验证“MCU 本地 1kHz 起步、阶梯到 10kHz 控制基线 + PC/ROS 高频下发 + ROS 状态/链路健康回传”的第一阶段可行性。

## 环境

- 板子：STM32F103RB，USART1 `/dev/ttyUSB0`，921600 8N1，DMA。
- Agent：`tools/run-bridge.sh /dev/ttyUSB0 921600`，默认 `MICROROS_AGENT_VERBOSITY=1`。
- 固件：新增 `com_control_task` 1kHz 本地控制骨架；2/5/10kHz 档切换到 TIM2 ISR；micro-ROS spin/read 等待收紧到 1ms 量级。
- PC 节点：`pc_cmd.launch.py`，QoS `RELIABLE / KEEP_LAST / depth=1`，`rtt_warn_ms=10`，`rtt_deadline_ms=50`。

### Latest-target status decimation

新增固件编译项 `EXO_STATUS_EVERY_N`：MCU 每条 PC 命令都更新本地 latest target，
但只按比例发布 `/com/tp_mcu_status`。这更贴近“PC 200Hz 下发目标，MCU 本地闭环消费最新目标，状态/链路健康另行回传”的控制分层。

| QoS / 配置 | PC 下发 | 状态回传频率 | 估算 MCU 收到 PC 目标 | 结果 |
|---|---:|---:|---:|---|
| reliable，`EXO_STATUS_EVERY_N=5` | 200 Hz | 约 14.4 Hz | 约 72 Hz | 比 full echo 约 40Hz 有改善，但仍远低于 200Hz |
| best-effort，`EXO_STATUS_EVERY_N=5` | 200 Hz | 约 32.3 Hz | 约 161 Hz | 当前最接近 200Hz 的 topic 模式 |

PC 侧新增 `tracking_mode:=sampled` 后，LinkHealth 不再预设“每条命令都必须 echo”，而是记录最近发出的 seq；实际状态回来后按 seq 回溯发送时间并统计 RTT。

| QoS / 波特率 / 配置 | PC 下发 | 状态回传频率 | 估算 MCU 收到 PC 目标 | LinkHealth |
|---|---:|---:|---:|---|
| best-effort，921600，`status_every_5`，sampled | 200 Hz | 约 30.7 Hz | 约 153 Hz | `lost=0 duplicate=0 inflight=0` |
| best-effort，2Mbps，`status_every_5`，sampled | 200 Hz | 约 31.9 Hz | 约 160 Hz | `lost=0 duplicate=0 inflight=0` |
| best-effort，3Mbps，`status_every_5`，sampled | 200 Hz | 约 28.6 Hz | 约 143 Hz | `lost=0 duplicate=0 inflight=0`，出现 0.845s 长间隔 |
| best-effort，921600，`status_every_10`，sampled | 200 Hz | 约 17.6 Hz | 约 176 Hz | `lost=0 duplicate=0 inflight=0` |
| best-effort，921600，`status_every_20`，sampled | 200 Hz | 约 9.26 Hz | 约 185 Hz | `lost=0 duplicate=0 inflight=0` |
| best-effort，921600，`status_every_40`，sampled | 200 Hz | 约 4.81 Hz | 约 192 Hz | `lost=0 duplicate=0 inflight=0`；曾遇到一次 ST-Link flash loader 瞬态失败，复位停核后重烧成功 |

因此 sampled/latest-target 模式的监控语义已经对齐：未抽样回传的目标不再被误报 lost。把状态回传降到 5Hz 量级后，MCU 接收 PC 目标已经接近 200Hz；2Mbps/3Mbps 没有带来线性收益，当前收益最大的方向是“命令 latest-only 高频下发，状态/诊断低频回传”。

## 结论

- 当前 `RELIABLE + micro-ROS serial + 921600 + F103` 往返闭环稳定点约为 20 Hz。
- 200 Hz 目标未达成；瓶颈不是单一 PC timer 或 agent 日志，固件已收紧到 1ms 后仍卡在约 40 Hz 状态回传。
- best-effort 能提高裸 topic 吞吐到约 80 Hz，但不能直接满足“每条控制命令可配对确认”的安全闭环要求。
- 2Mbps 能建链，说明物理层可跑更高波特率；但 reliable 闭环只从约 42Hz 提到约 46Hz，收益不足以支撑 200Hz。
- `EXO_CONTROL_LOOP_HZ=1000/2000/5000/10000` 四档已通过编译验证；2/5/10kHz 使用 TIM2 ISR，不占 control task 栈，RAM 从 15.6KB 降到约 15.0KB。
- 2/5/10kHz 真机运行期烟测均能保持 20Hz PC 命令无 lost；RTT 仍主要落在 20-30ms 区间，说明“MCU 本地闭环提频”和“PC/ROS 往返通信延迟”需要分开优化。
- latest-target 方向有实质收益：`best_effort + status_every_40 + sampled monitor` 反推 MCU 可接收约 190Hz PC 目标，已经接近“PC/ROS 200Hz 下发，MCU 本地闭环消费最新目标”的目标形态。
- 恢复默认固件后，20Hz smoke 可建图并正常收发；连续短测出现过单次 `lost=1 duplicate=1`，RTT 约 55ms，需继续观察是否为 reset 后瞬态或链路抖动。后续单独复测 20Hz 为 `sent=140 matched=139 lost=0 duplicate=0 inflight=1`。
- 后续优化应优先验证：
  - 进一步拆分控制命令与诊断状态：控制命令保持 latest-only / best-effort，状态诊断考虑降频或独立通道。
  - XRCE stream history、MTU、baudrate 对吞吐的影响。
  - MCU 本地控制闭环继续保持独立，PC/ROS 不参与每个 motor-control tick。
